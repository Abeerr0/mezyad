# تحديث الباك — برانش عبير

التاريخ: 20 أكتوبر 2026. الأساس: `ecff165` على `abeer`.

## التعديلات

- رفع الصور مع الإعلان وتعديل الإعلان المرفوض وحقول التصنيف.
- فحص الصور وحجمها وعددها، وإزالة الملفات الجديدة إذا فشل الحفظ.
- عرض الصور بروابط مؤقتة من الاستجابات المصرح بها.
- التحقق من المعرفات وسبب الرفض، وحماية محاولات رمز المزاد الخاص.
- تحديث حالات المزادات بوقت قاعدة البيانات، وفلاتر التصنيف والحالة.
- مراقبة المزادات للمشرف، والتحقق من الوصول عند قراءة الالتزام الخاص.
- تشغيل اختبارات الداتا والمزايدة والإغلاق الموجودة سابقًا داخل حزمة QA.
- أمر `npm run db:setup` لإنشاء الجداول والتصنيفات الموجودة دون بيانات مشاركة وهمية.
- التعليقات في الأجزاء الجديدة مختصرة وبالعربي. لا Redis ولا Socket.io ولا مدفوعات حقيقية.

## حدود التسليم

لم يتم اختيار مزود الأوبن بنك حسب تأكيد عبير. `bank.js` نقطة الربط فقط، وليس
تكاملًا مكتملًا. لم تتم إضافة موافقة تجريبية داخل التطبيق. اختبارات المزايدة
التي تحتاج SUCCESS تستخدم بيانات مصطنعة داخل قاعدة اختبار معزولة فقط.

GitHub رفض رفع التعديلات برسالة `403 Resource not accessible by integration`.
التعديلات محفوظة في نسخة العمل المحلية وcommit على `abeer`؛ ليست منشورة على
البرانش البعيد. يلزم أن يتيح مالك الريبو صلاحية كتابة لاتصال GitHub أو أن ترفعها
عبير من حساب عنده صلاحية.

PostgreSQL المحلي غير متاح في هذه البيئة. اختبارات الداتا موجودة لكن لم تنفذ؛
لا يُعد غياب أخطاء الاختبارات المتخطاة نجاحًا للداتا. فحص CI على PostgreSQL 16
يلزم بعد رفع البرانش. لا يوجد إثبات لتكامل بنكي أو رحلة متصفح كاملة.

واجهات البيع والمشاركة موجودة تحت `Stage_4/` وخارج التطبيق المبني في
`frontend/src/`. ربط هذه الواجهات عمل فرونت منفصل.

## نتائج التنفيذ المحلي

- `npm run check`: نجح فحص ملفات الباك.
- `npm test` في الباك: 75 إدخال اختبار؛ 12 نجحت، صفر فشل، 63 متخطّاة لغياب PostgreSQL.
- `npm test` في الفرونت: 31 اختبارًا نجحت، صفر فشل.
- `npm run build` في الفرونت: نجح.
- اختبارات الملفات المحلية فحصت تحويل الصور إلى JPEG، وتنظيف الملفات عند الفشل،
  ومنع الروابط غير الموقعة أو المعدلة أو المنتهية. لا تثبت نتائجها معاملات PostgreSQL.

## المتبقي بالترتيب

1. إتاحة الكتابة إلى الريبو ثم رفع `abeer` ومراجعة تشغيل GitHub CI على PostgreSQL 16.
2. معالجة أي فشل يظهر في اختبارات الداتا، ثم توثيق النتائج الفعلية.
3. اختيار مزود sandbox وتحديد عملية الالتزام وقاعدة التحقق حسب Stage 3.
4. تنفيذ الربط الرسمي واختبار النجاح والرفض والمهلة، ثم رحلة عامة وخاصة كاملة.

لا يصح وصف الباك أو المشروع بأنه مكتمل 100% قبل هذه الخطوات.
